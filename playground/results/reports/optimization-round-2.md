# OBS and privacy optimization experiments

All measurements below are exploratory, on the user's Apple M1 Pro with other applications running. No numbers constitute a privacy guarantee. The existing live OBS worker was restored to 15 fps / 15 seconds after the trials.

## Video transfer and OBS GPU source

The normal native output no longer JPEG-encodes every frame when there are no browser-preview clients. The browser preview starts encoding again on subscription; the native path still receives only the redacted frame. `test_obs_native.py` checks both native and browser transport. On 120 sampled 1280 × 720 frames, JPEG encoding median/p95 was 4.05/17.76 ms and BGR-to-BGRA conversion plus bytes allocation was 0.43/1.28 ms; these are separate operations under variable load, not an end-to-end speedup or proof of zero-copy. The production path still captures using OBS virtual camera, converts and copies frames, and sends processed frames over a socket.

A separate uninstalled OBS source prototype (`obs-plugin/gpu-prototype.c`, `gpu-prototype.effect`, and `experiments/rust-comparison/gpu_worker.py`) sends the delayed original frame and its binary mask together in one private local packet and applies an experimental blur effect in the OBS graphics subsystem. This is a custom OBS source, not yet the requested direct filter on an existing video source: it still uses the virtual camera and CPU/socket copies and transmits unredacted pixels locally. The packet integrity test checks same-packet frame/mask content, mask dimensions and binary values, and user-only socket permissions. Receiver tests check complete frame receipt, disconnect clearing, and the 500 ms staleness predicate. A standalone libobs test loaded the source, received synthetic paired data, and rendered it on the Mac's OBS OpenGL graphics backend. A synchronized 30-render offscreen loop reported about 456 renders/s on one repeating synthetic frame; this excludes inference, capture, video variation and actual OBS output and is not a stream FPS result. This prototype is not installed in or connected to the user's OBS scene.

The first shader left a 600-pixel QR code decodable. After changing the sampling radius, OpenCV's decoder failed to decode generated masked QR codes of 120, 240, 400 and 600 pixels, and Apple Vision did not recognize three generated masked phone-text samples. That narrow synthetic check is insufficient to show real QR/text cannot be reconstructed. The shader, partial masks, color formats, boundaries, multiple codes, actual video, metadata corruption, disconnect/underlying-scene behavior and frame-to-detection correctness require further tests before use.

## Sparse tracking reuse

A cProfile run of 480 frames with prerecorded detections spent about 8.83 cumulative seconds in `carry`/`move` while building masks, versus 1.26 seconds in blur; this is a replay profile, not a live detector profile. `cached_tracking.py` caches the unrounded forward position of a detection's box and advances it as the output frame advances, keeping the original calculation for cases it cannot reuse. A randomized test compares ordered and out-of-order box propagation. Three separate 240-frame recorded-detection segments (bench, bench2, and rotated rot2) produced byte-identical masks in repeated baseline/cached runs. Representative baseline/cached processing times were 4.63–5.42 / 2.90–3.14 seconds, 4.48–4.76 / 3.08–3.81 seconds, and 2.97–3.09 / 2.38–2.52 seconds. These exclude live detection; identical masks do not improve existing misses. On the rotated segment, the test counted 239/240 QR and 155/240 phone labels covered in both variants.

On a 30-fps labeled benchmark replay through the actual OBS native source, baseline runs reported 29.99 fps with 0 dropped and 28.40 fps with 32 dropped; cached runs reported 30.04 and 30.10 fps, with 0 dropped. Runs were sequential in baseline/cached/cached/baseline order, 20 seconds each after warmup, with a 5-second buffer; workload and system load varied. These are worker counters, not independent OBS-display frame measurements.

In separate changing live footage via OBS virtual camera, the experimental cached worker with 30-fps target reported 30.01 output fps over 35.29 seconds, 0 additional drops, 0 additional full-frame failsafes and 0 late detections; median sampled internal delay was 5.009 seconds. At 60-fps target it reported 61.15 output fps over 32.2 seconds with 0 additional drops in that interval, but 148 drops had occurred before it. OBS was configured at 30 fps, the virtual-camera input may contain duplicates, and output rates above 60 indicate burst timing. This does not establish actual 60-fps unique displayed output. No live frame-by-frame privacy evaluation was performed. `obs_cached.py` remains experimental and is not the default worker.

## Adaptive cadence and conservative mask reuse

The bounded adaptive scheduler remains experimental. In an offline 240-frame replay with cached per-frame detections, fixed every-six-frame and adaptive schedules made 40 and 42 detector calls, respectively, and both covered 240/240 QR and 240/240 phone boxes on that segment. Those do not represent real detector time, all clips, or bystander coverage. A synthetic small one-frame change did not trigger the coarse motion heuristic; a periodic 0.2-second maximum gap cannot protect a transient event appearing between scans. Do not enable this scheduler as a privacy guarantee. Prior union and motion-aware reuse experiments exposed reference-mask pixels; see `mask-reuse-experiment.md` and `motion-mask-reuse.md`.

## Platform execution and OCR crops

The experimental platform probe chooses Core ML on macOS when available, DirectML on Windows when available, and CPU otherwise. The probe ran the screen model on this Mac and reported Core ML plus CPU fallback, median 15.5 ms. Windows/DirectML and Windows ML runtime installation were not tested; this is a model probe, not a Windows implementation of the Apple Vision/OCR/live OBS pipeline. Windows ML has multiple API surfaces and the newer Runtime API is documented as experimental; check [Microsoft's documentation](https://learn.microsoft.com/windows/ai/new-windows-ml/runtime/overview) before choosing a production integration.

The existing OCR path performs full-frame Apple Vision and additionally scans detected-screen crops; this behavior was retained. On 12 sampled frames from one benchmark, full-frame Vision alone covered 8/12 labeled QR and 7/12 phone boxes; adding screen crops did not increase these counts. The separate QRDet model and temporal masking were excluded, so this is not an overall detector-recall measurement. Excluding the first cold sample, median full Vision was 106 ms and screen detection plus crop work added 100 ms on the busy Mac. This small sample does not justify removing crop OCR or claiming a performance benefit from it.

## Remaining work

The requested direct OBS GPU filter, zero-copy capture/transport, platform-complete Windows support, validated live adaptive scheduling, and privacy-safe mask-reuse deployment are not complete. User-facing output still uses the current CPU redaction path. Test real QR/phone/face labels frame by frame, false exclusions and short transient exposures, full system memory/CPU/GPU and actual displayed FPS, multiple hardware configurations, packet invalidation, downstream scene composition, shutdowns, and sustained operation before changing defaults. The selected-person mismatch observed earlier is not resolved.

## Follow-up integration

The box-position cache is now in the shared CPU redactor. The original calculation remains in `compare_tracking.py`; after integration its masks matched bit-for-bit on 240 benchmark frames in four alternating runs. Random ordered and out-of-order carry paths also matched the uncached calculation. During a separate 33.43-second live test, the integrated worker at a 30-fps input target and 5-second buffer reported 30.00 output fps, 0 additional drops, 0 additional fail-safe frames, 0 additional late detections and a sampled internal median delay of 5.013 seconds. Before that measurement it had already dropped 19 frames and produced 35 fail-safe frames. OBS was set to 30 fps; unique displayed frames and live privacy were not measured. Live content and background workload differed from previous trials, so this is not a controlled before/after speed comparison. Afterward the worker was restored to 15 fps and the original 15-second buffer with the same reference photos.

The isolated GPU module additionally registers an experimental OBS filter and draws an opaque black texture for stale or absent paired packets. The source and filter compile, and the receiver checks the stale predicate; the synthetic source render was tested in standalone libobs. The filter attached to a real OBS source, downstream scene composition, stale output as observed in a scene, and actual timestamped camera/video synchronization remain unverified. It is not installed or used for protected output. The packet still uses full-frame CPU copies and the OBS virtual camera. The Windows inference probe and scheduler remain experimental, and no Windows execution or short-exposure privacy guarantee was established.
